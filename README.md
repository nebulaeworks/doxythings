# doxythings

Test, coverage and benchmark results, linked into Doxygen documentation.

Doxygen docs can be the main way into a codebase. doxythings adds results
to them, linked both ways between the code and the results. Benchmarks come
first:

- each **benchmark** shows its own results,
- each **entity it measures** (function, class...) gets a collapsible
  Performance section linking to those benchmarks,
- an **overview page** lists every result, linked to both.

doxythings is a single binary with no dependencies besides Doxygen itself,
and doesn't depend on any build system.

## Installing

```sh
go install github.com/nebulaeworks/doxythings/cmd/doxythings@latest
```

or, from a checkout, `make build` (binary in `bin/`).

## Tagging benchmarks

Run `doxythings init --dir <dir>` to write `doxythings.doxyfile` (the tag
definitions and stylesheet) into `<dir>`, `@INCLUDE` it at the end of your
Doxyfile, then tag each benchmark's doc comment, ideally at the end:

```cpp
/**
 * A flat array of numbers: one recursion level, no object allocations.
 *
 * @benchmark_run{ToCoreJson/FlatArray}
 * @benchmarks{kora::schema::detail::to_core_json}
 */
static void ToCoreJsonFlatArray(benchmark::State &state) { ... }
```

- `@benchmark_run{Name}`: which results belong to this benchmark. Matches
  `Name` exactly, or any `Name/...`, so one tag covers a parameterised
  benchmark's runs. Invisible in the HTML.
- `@benchmarks{symbol}`: what it measures. Shown as a link, and listed on a
  "Benchmark Index" page.

Both can repeat.

## How it works

Doxygen resolves the tags; doxythings joins them with the results:

1. Run Doxygen with `GENERATE_XML = YES` (HTML not needed).
2. Run doxythings on that XML plus the benchmark results:
   ```sh
   doxythings doxygen \
       --xml-dir build/doxygen/xml \
       --output build/docs-generated/benchmarks.dox \
       --fragments-dir build/doxythings-fragments \
       results/*.json
   ```
3. Run Doxygen for real, with `benchmarks.dox`'s directory on `INPUT` and
   the fragments directory on `EXAMPLE_PATH`.

doxythings reports anything it couldn't match (results no benchmark claims,
tagged benchmarks with no results, unknown `@benchmarks` targets) on
stderr; `--strict` makes that an error.

Without `--xml-dir` it writes the overview page only, without links.
`doxythings html --output report.html results/*.json` writes the overview as
a standalone page instead.

With CMake, CMakeItSo's `add_benchmark_target` (see its `doxythings.cmake`)
runs all of this as a `bench` target.

## Inputs

Google Benchmark JSON (`--benchmark_out_format=json`).

## Design

Reading, linking and rendering are separate stages, so new input formats
and new kinds of results can be added without touching the others:

| Package             | Role                                                              |
|---------------------|-------------------------------------------------------------------|
| `internal/gbench`   | reads Google Benchmark JSON into the model                        |
| `internal/model`    | results, independent of any harness or output format              |
| `internal/tags`     | the documentation tags: their Doxygen aliases and XML form        |
| `internal/doxygen`  | reads Doxygen's XML into entities and their tags                  |
| `internal/link`     | matches results to benchmarks and benchmarks to measured entities |
| `internal/render`   | writes Doxygen input or a standalone page from model and links    |
| `internal/host`     | hardware details of the current machine                           |
| `internal/assets`   | the files `init` writes, compiled into the binary                 |
| `internal/cli`      | the command line, wiring the stages together                      |

## Development

```sh
make test   # go vet + go test; the end-to-end test needs doxygen on PATH
make docs   # this repository's Doxygen docs, in build/docs/html
```

The docs are generated by Doxygen through `tools/doxygo`, an input filter
that rewrites Go into C++-shaped declarations Doxygen can parse. Every
entity, exported or not, must be documented, with every parameter and
result: the docs build fails on anything missing.

Doc comments follow the C++ projects' style:

```go
/**
 * Lookup returns the entity with this RefID, and whether there is one.
 *
 * @param refID The entity's Doxygen id.
 * @return The entity, and whether there is one.
 */
func (x *Index) Lookup(refID string) (*Entity, bool) {
```

with `/** One line. */` for struct fields. doxygo reads `//` comments the
same way, and any Doxygen command or Markdown works in either. On top of a
plain C++ translation it:

- resolves calls with the Go type checker, adding "References",
  "Referenced by" and call/caller graphs Doxygen can't derive from Go;
- shows the module's interfaces a type implements as base classes, so
  "Implements"/"Implemented in" links and inheritance graphs appear, and a
  method documented only as "Name implements Iface." copies Iface's docs;
- turns imports into includes, giving each file an include graph and each
  directory a package dependency graph;
- turns Go doc links (`[Name]`, `[pkg.Name.Method]`) into Doxygen
  references, or pkg.go.dev links for other modules;
- documents a file with a `/** @file ... */` comment before the package
  clause, which Go ignores.

The type-checked index is cached in the user cache directory between
files; set `DOXYGO_CACHE=off` to disable that, or to a directory to use it
instead.
